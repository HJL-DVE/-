## 六、验证过程中的工具性缺陷（非产品缺陷，一并记录避免重复踩坑）

| # | 现象 | 原因 | 处理 |
| --- | --- | --- | --- |
| 1 | 首次改 `Integer days`→`String daysRaw` 后 days=abc 仍不报错 | Spring 的 `defaultValue` 会静默吞掉类型绑定异常 | 去掉 defaultValue，方法内归一化 |
| 2 | 去掉 defaultValue 后 days=30 仍返回 7 | Spring 按**参数名**绑定，`daysRaw` ≠ `days`，契约被破坏 | 显式 `@RequestParam(name="days")` |
| 3 | 批量正则替换破坏了 `ReportController` 语法 | 正则跨行匹配不可靠 | 还原文件，改用行级精确编辑 + 括号平衡校验 |
| 4 | 小程序 pages.json 被字符串替换破坏 | 该文件是格式化 JSON，非紧凑格式 | `git checkout` 还原，改用 JSON.parse/stringify |
| 5 | 24 号回归脚本导致会员表消失 | 该脚本故意 RENAME 表制造 DLQ 失败，中途崩溃则不恢复 | 已加四重进程守护（exit/SIGINT/uncaughtException/unhandledRejection） |
| 6 | PowerShell 执行 docker exec mysql 时输出为空 | stderr 混入导致管道吞掉输出 | 改用 node spawnSync + `MYSQL_PWD` 环境变量 |

### 本次为混合部署补充的能力

order-service 的 CouponInternalClient / PointsInternalClient 增加 url 配置项（留空=走 Nacos 服务发现，生产行为不变）：

~~~yaml
# order-service/src/main/resources/application.yml
teaclub:
  client:
    marketing-url: ${TEACLUB_MARKETING_URL:}
~~~

设置 TEACLUB_MARKETING_URL=http://127.0.0.1:9007 后，Feign 改走宿主映射端口直连，
从而支持「营销服务在容器、订单服务在宿主机」的混合部署形态。
### 混合部署支持的最终形态（实测结论）

经多轮验证，确定以下事实：

| 部署形态 | Gateway 路由 | 服务间 Feign | 结论 |
| --- | --- | --- | --- |
| 全容器 | OK（服务名互通） | OK | ✅ 推荐 |
| 全宿主机 IDEA | OK | OK | ✅ 推荐 |
| 混合（部分容器部分宿主） | ❌ 容器注册 Docker 内网 IP，宿主机不可达 | ❌ 同上 | ❌ 不可行 |

Docker Desktop（WSL2 后端）下宿主机**无法路由**到容器网段 172.18.0.0/16（实测 TCP 超时），
容器**可以**路由到宿主机。因此混合部署只能单向工作，无法构成完整链路。

本次为此补充了能力（均为可选、默认行为不变）：

- `order-service` 的 `CouponInternalClient` / `PointsInternalClient` 支持 `url` 直连：

~~~yaml
# order-service/src/main/resources/application.yml
teaclub:
  client:
    marketing-url: ${TEACLUB_MARKETING_URL:}
~~~

  留空 = 走 Nacos 服务发现（生产默认）；设置后 Feign 改走宿主映射端口。

- 各服务 `application-docker.yml` 增加 `spring.cloud.nacos.discovery.ip: ${DISCOVERY_IP:}`，
  compose 增加 `DISCOVERY_IP` 变量位。**实测 Nacos 2025 版该属性未参与 IP 选择**，
  保留作为后续探索项（不影响默认行为）。

**结论**：开发期建议统一用「全 IDEA」或「全 Docker」，避免混用。
