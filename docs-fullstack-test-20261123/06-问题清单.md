## P1-02 积分调整可向不存在的会员写入脏数据

| 字段 | 内容 |
| --- | --- |
| **ID** | P1-02 |
| **模块** | marketing-service / 积分管理 |
| **严重级别** | P1 |
| **问题描述** | `POST /api/admin/marketing/points/adjust?memberId=<不存在的ID>&points=100` 返回 `code=0 成功`，并凭空创建 `mkt_points_account`（积分账户）与 `mkt_points_transaction`（积分流水）。运营侧无法察觉「调整成功了但会员根本不存在」，且会持续污染会员维度报表 |
| **复现步骤** | 1. admin 登录<br>2. `POST /api/admin/marketing/points/adjust?memberId=999999999&points=100`<br>3. 查 `mkt_points_account WHERE member_id=999999999` → 存在一条 |
| **期望结果** | 返回业务错误码（如 10004 会员不存在），不产生任何账户与流水 |
| **实际结果** | 返回成功并创建脏账户（100 积分）+ 脏流水（ADJUST 类型） |
| **证据** | 实测输出：`不存在会员 code=0 ok`；DB 查询 `mkt_points_account member_id=999999999` → 1 条（total_points=100）、`mkt_points_transaction` → 1 条 |
| **影响** | 数据完整性缺陷；积分报表虚增；异常难排查 |
| **修复建议** | `PointsServiceImpl.adjust` 增加 `requireMemberExists(memberId)`，经 member-service 内部接口确认会员存在；member-service 不可用时拒绝放行（宁可拒绝一次人工调整，也不写脏账户） |
| **状态** | ✅ **已修复**（提交 `6fd1297`），实测返回 `10004 会员不存在`，DB 脏数据已清理 |

## P2-02 非法 days 参数被伪装成系统内部错误

| 字段 | 内容 |
| --- | --- |
| **ID** | P2-02 |
| **模块** | report-service / 报表 |
| **严重级别** | P2 |
| **问题描述** | `GET /api/report/dashboard/trend?days=abc` 返回 `50000 系统内部错误`。Spring 参数绑定抛 `NumberFormatException`，被全局异常处理器兜底成 50000 —— 既不符合错误码语义（应是 10001 参数错误），也把「用户传错参数」伪装成「服务端故障」，且会打印完整堆栈 |
| **复现步骤** | `curl -H "Authorization: Bearer $TOKEN" "http://127.0.0.1:9008/api/report/dashboard/trend?days=abc"` |
| **期望结果** | `code=10001`，message 指出 days 必须是整数 |
| **实际结果** | `code=50000`，message「系统内部错误」 |
| **证据** | 实测：`days=abc → code=50000 系统内部错误`；`days=30 → code=0 长度=7`（应为 30，说明 defaultValue 静默吞异常） |
| **影响** | 错误码语义错误；堆栈日志噪音；前端无法区分「参数错」与「服务故障」 |
| **修复建议** | `ReportController` 11 处 days 参数统一 `@RequestParam(name = "days", required = false) String daysRaw` + `parseDays()` 归一化 |
| **状态** | ✅ **已修复**（提交 `a3b7fcd`），实测 `days=abc → 10001 days 必须是整数: abc`，`days=30 → 长度 30` |

> **修复过程中的两处返工（经验记录）**：
> 1. 第一版保留 `@RequestParam(defaultValue="7")`：Spring 的 defaultValue 会**静默吞掉**类型绑定异常 → `days=abc` 悄悄回落默认值，不报错。
> 2. 第二版把参数名从 `days` 改成 `daysRaw`：Spring **按参数名绑定**，客户端传的 `?days=` 收不到 → 连正常值 `days=30` 都变成默认值 7，**接口契约被破坏**。
> 最终方案：显式 `name="days"` 保留契约 + 去掉 defaultValue + 方法内归一化。

## P2-03 小程序 BASE_URL 硬编码局域网 IP

| --- | --- |
| **ID** | P2-03 |
| **模块** | 小程序 / 配置 |
| **严重级别** | P2 |
| **问题描述** | `src/utils/request.ts` 中 `export const BASE_URL = 'http://192.168.3.34:9000'` 硬编码。小程序工程没有 .env 机制（管理后台有），换网络/换机器即失效；正式发布后 `http://` 明文域名会被微信平台拦截 |

| **影响** | 演示环境脆弱；无法发布生产 |
| **修复建议** | 引入 `.env` + `VITE_GATEWAY_URL`；生产用 HTTPS 域名并在微信后台配 request 合法域名；或提供「自定义服务器地址」调试入口 |

## P2-04 容器与宿主机不能混合部署

| 字段 | 内容 |
| --- | --- |
| **ID** | P2-04 |
| **模块** | 部署 / 架构 |
| **严重级别** | P2 |
| **问题描述** | 部分服务跑在 IDEA（宿主）、部分跑在 Docker（容器）时：容器服务注册到 Nacos 的地址是 Docker 内网 IP（172.18.x.x），宿主机上的 Gateway 路由不到（返回 10302），宿主机服务通过 Feign 调容器服务也失败（TCP 超时）。容器调宿主则正常 |
| **复现步骤** | 1. IDEA 启动 gateway + order<br>2. docker 启动 marketing-service<br>3. 请求 `/api/report/...` → 10302；order 的券抵扣 → 0 |
| **期望结果** | 混合部署可用（开发期常见诉求） |
| **实际结果** | 必须「全容器」或「全宿主机」二选一 |
| **证据** | Nacos 实例列表显示 `report-service: 172.18.0.6:9008`；宿主机 TCP 连接 172.18.0.7:9007 **超时** |
| **影响** | 开发期无法按需混合；联调链路被环境打断 |
| **修复建议** | 已在各服务 `application-docker.yml` 增加 `spring.cloud.nacos.discovery.ip: ${DISCOVERY_IP:}` 与 compose 的 `DISCOVERY_IP` 变量位，但**实测未生效**（Nacos 2025 版该属性疑似不参与 IP 选择）。后续可改用自定义 `NacosDiscoveryProperties` 覆写或直接指定注册 IP |
| **状态** | ⏸ 部分处理（配置位已预留，机制未验证生效） |
