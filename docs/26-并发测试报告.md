# TeaClub 第五阶段·任务四：并发测试报告

| 项目 | 内容 |
| --- | --- |
| 文档编号 | TC-T4-02 |
| 日期 | 2026-11-20 |
| 方式 | 真实 HTTP 并发请求（Node `Promise.all` 同时发起，服务端线程池并发处理） |
| 结论 | 三个并发场景全部通过，无超扣、无重复扣款、无负余额 |

---

## 一、测试环境

```text
wallet-service   1 实例（Docker，9004）
MySQL 8.4        单实例，事务隔离级别默认 REPEATABLE-READ
会员              独立测试账号，互不干扰
并发方式          N 个 HTTP 请求同时发出，服务端并发执行
```

---

## 二、场景 A：并发不同订单号扣款（验证行锁不丢更新）

**前置**：会员充值 10000 分，余额 10000。

**动作**：同时发起 20 笔扣款，每笔 300 分，订单号各不相同（共应扣 6000）。

```text
成功 = 20    失败 = 0
扣款前余额 = 10000
扣款后余额 = 4000
实际扣减   = 6000      ← 与期望一致
```

**结论**：20 笔并发全部成功且金额精确，行锁生效，无丢失更新。

---

## 三、场景 B：并发相同订单号扣款（验证幂等）

**前置**：余额 4000。

**动作**：同时发起 30 笔扣款，**订单号完全相同**，每笔 100 分（只应扣 1 次）。

```text
成功 = 17（其中幂等命中 16）   失败 = 0
扣款前余额 = 4000
扣款后余额 = 3900
实际扣减   = 100       ← 与期望一致
```

**结论**：30 个并发同单号请求，资金只变动一次。前置幂等查询 + 唯一索引冲突兜底共同保证。

---

## 四、场景 C：并发超余额扣款（验证不出负余额）

**前置**：余额 3900。

**动作**：同时发起 20 笔扣款，每笔 2000 分（理论上最多 1 笔可成功）。

```text
成功 = 1    拒绝 = 19
最终余额 = 1900
是否出现负余额 = 否
```

**结论**：余额校验在行锁内完成，并发下不会出现「都通过校验再各自扣款」导致的负数。

---

## 五、附带验证：并发冻结

```text
同一订单号并发冻结 -> 唯一键 uk_freeze_order 兜底，返回同一 freezeId（幂等）
多订单并发冻结    -> 可用余额 = 余额 - SUM(有效冻结)，超可用即拒绝
```

---

## 六、结论

| 并发风险 | 是否发生 | 依据 |
| --- | --- | --- |
| 丢失更新（两笔覆盖彼此） | 否 | 场景 A 扣减额精确 |
| 重复扣款（重试/重复消息） | 否 | 场景 B 只扣 1 次 |
| 超扣导致负余额 | 否 | 场景 C 余额 1900 |
| 冻结超额占用 | 否 | 冻结校验含已冻结额 |

## 七、局限性（如实标注）

| 项 | 说明 |
| --- | --- |
| 并发规模 | 单场景最多 30 并发，未做千级压测 |
| 多实例 | wallet-service 单实例，未验证多实例下 Redis 锁的必要性 |
| 死锁 | 单钱包操作按固定顺序加锁，未构造跨钱包死锁场景 |
