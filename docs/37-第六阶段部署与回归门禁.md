## 一、Web 管理后台部署（同源反代）

### 1.1 为什么要同源

浏览器里写的 `http://127.0.0.1:9000` 指的是**用户自己的机器**。远程部署时该地址根本不存在；
即便是本机部署，也会多一次跨域。因此生产必须同源：

```text
浏览器 ──> Nginx:80 ──┬── /            → Vue dist（history 回退 index.html）
                      └── /api/...     → gateway-service:9000（docker 网络内按服务名）
```

对应地 `.env.production` 的 **`VITE_API_BASE_URL` 必须留空**（前端走相对路径）。
代码层面无需改动：`request.ts` 中 `API_BASE_URL = import.meta.env.VITE_API_BASE_URL || ''`
本来就支持留空。

### 1.2 交付物

| 文件 | 作用 |
| --- | --- |
| `deploy/web/Dockerfile` | 两阶段构建：node:22-alpine 构建 → nginx:1.27-alpine 运行 |
| `deploy/web/nginx.conf` | history 回退、`/api/` 反代、gzip、安全头、`/healthz` |
| `backend/infrastructure/docker/docker-compose.web.yml` | 叠加式编排，独立于后端服务集合 |
| `frontend/teaclub-admin/.env.production` | `VITE_API_BASE_URL=`（留空）+ 超时 20s |

> 单独成 `docker-compose.web.yml` 而不并入主 `docker-compose.yml`：
> 前端构建上下文需要**仓库根**（同时拿 `frontend/` 与 `deploy/`），
> 而后端各服务上下文是各自的服务目录，混在一起会打乱约定。

### 1.3 启动

```bash
cd backend/infrastructure/docker
docker compose -f docker-compose.yml -f docker-compose.web.yml \
  --env-file .env.docker up -d
```

访问 `http://127.0.0.1:8080`（端口可用 `WEB_PORT` 覆盖）。

### 1.4 实测（全部真实请求）

## 二、支付渠道语义修正

### 2.1 问题

`PayCreateRequest.channel` 被写成 `private String channel = "WECHAT_JSAPI";`。
这导致 **「不传 channel」与「显式传 JSAPI」在服务端无法区分**：

- 桌面收银台需要 Native 二维码（`codeUrl`），但请求若不带 channel 就被当成 JSAPI，拿不到 `codeUrl`；
- 之前脚本 19 出现「订单支付无 codeUrl」正是这个原因，而收银台页面因为**显式传了** `WECHAT_NATIVE` 才侥幸正常。

### 2.2 修复

| 改动 | 内容 |
| --- | --- |
| DTO | 去掉 `= "WECHAT_JSAPI"` 默认值，改为 `null` |
| Service 接口 | 拆成两个入口：`createPayment`（管理端）/ `createPaymentForMember`（会员端） |
| 默认渠道 | 管理端 → `WECHAT_NATIVE`；会员端 → `WECHAT_JSAPI` |
| 渠道白名单 | `WECHAT_NATIVE / WECHAT_JSAPI / MOCK_NATIVE / MOCK`，非法值直接 `PARAM_INVALID` |
| 会员端降级 | 有 openid 走 JSAPI；无 openid 自动降级 Native（否则微信必拒） |

两个入口**只差默认渠道**，金额校验、状态机、归属校验、事件发全部共用。

### 2.3 实测（`20-payment-channel.mjs`，6/6）

| 场景 | 期望 | 实测 |
| --- | --- | --- |
| 管理端不传 channel | Native + codeUrl | channel=WECHAT_NATIVE，codeUrl 有值 |
| 管理端显式 JSAPI | JSAPI + invokeParams | channel=WECHAT_JSAPI，invokeParams 有值 |
| 非法 channel=BITCOIN | 拒绝 | code=10001，提示可选值 |
| 会员端带 openid | JSAPI | channel=WECHAT_JSAPI |
| 会员端无 openid | 降级 Native | channel=WECHAT_NATIVE，codeUrl 有值 |

## 三、统一回归门禁

### 3.1 一条命令

```bash
node backend/infrastructure/test/run-regression.mjs
```

支持过滤：

```bash
node run-regression.mjs smoke      # 只跑冒烟
node run-regression.mjs 17 18      # 按序号
node run-regression.mjs refund     # 按标签
```

行为：
1. 先探测网关 60 秒，未就绪直接给出容器启动命令并退出码 2；
2. 顺序执行各脚本，提取脚本自己打印的 `汇总: PASS=n FAIL=m`；
3. 任一脚本非 0 退出即整体失败，只回放该脚本的 FAIL 行（避免刷屏）；
4. 末尾汇总脚本数、断言总数、总耗时。

### 3.2 当前门禁结果

```text
▶ 17-phase6-smoke.mjs               ✔ PASS=28  FAIL=0   0.7s
▶ 18-recharge-pay-closed-loop.mjs   ✔ PASS=17  FAIL=0   3.6s
▶ 19-refund-via-gateway.mjs         ✔ PASS=14  FAIL=0   2.0s
▶ 20-payment-channel.mjs            ✔ PASS=6   FAIL=0   0.4s
▶ 12-fund-invariants.mjs            ✔ PASS=6   FAIL=0   0.5s
========================================================
脚本  通过 5/5
断言  PASS=71  FAIL=0
========================================================
```

### 3.3 顺带修好的脚本缺陷

`12-fund-invariants.mjs` 原先**只打印查询结果，没有任何断言**，
在门禁里表现为 `PASS=0 FAIL=0`（看起来像"什么都没验"）。
已重写为真正的 I1–I6 断言：

| 编号 | 断言 | 实测 |
| --- | --- | --- |
| I1 | 无负余额 | 钱包数=14，负余额=0 |
| I2 | 余额 == 流水累计 | 不守恒=0 |
| I3 | 单笔 `after == before + change` | 不自洽=0 |
| I4 | 链式衔接 `before == LAG(after)` | 断裂数=0 |
| I5 | `(biz_type, biz_no)` 唯一 | 重复组数=0 |
| I6 | 有效冻结额 ≤ 账户余额 | 超冻笔数=0 |

> 另注：该脚本退出码在 PowerShell 下曾被误判为 1，
> 实际是 mysql 客户端把「命令行传密码」的 Warning 写到 stderr，
> 用 `*> 文件` 重定向后确认 `NODE_EXIT=0`。门禁本身用 `spawn` 直接读子进程退出码，不受此影响。
