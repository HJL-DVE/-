## 一、问题：失败的消息会静默丢失

受控实验（临时把 `mem_member` 改名让业务必然失败）：

| 观察点 | 修复前 |
| --- | --- |
| 消费者是否报错 | ✅ 抛 `BadSqlGrammarException` |
| 消息是否进 DLQ | ❌ `dlq.messages=0` |
| 队列统计 | `deliver=1 redeliver=0` |
| 业务数据 | ❌ 会员累计消费仍为 0，订单已 PAID → **永久不一致** |

即：**消息消费失败后既没重投也没进死信，直接消失了**。

## 二、定位到的 3 个真实缺陷

### 缺陷 1：Redis 幂等键未按消费者隔离（最严重）

`MessageIdempotencyGuard` 用 `mq:consumed:{eventId}` 做键，**不含队列名**。
而 `ORDER_PAID` 被 member-service 与 marketing-service **同时订阅**（正常的 fan-out），两者共用同一个 Redis：

```text
14:18:36  marketing-service 消费成功 → 写入 mq:consumed:{eventId}
14:18:36  member-service 看到该键   → 判定"重复消息" → 跳过
```

后果：marketing 拿到积分，member 的消费档案**永远不更新**，
日志显示「重复消息已忽略」看起来完全正常 —— 排查极其困难。

**修复**：键改为 `mq:consumed:{queueName}:{eventId}`，
队列名取 `messageProperties.getConsumerQueue()`（Spring AMQP 自动填充），一消费者一键。

### 缺陷 2：签到积分流水 bizNo 不含会员 ID

`uk_points_biz(brand_id, biz_type, biz_no)` 的唯一约束下，
签到用的 bizNo 只有日期 `20261120`。同一天**第二个会员**签到时会撞上第一个人的流水，
`selectByBiz` 命中后 `doEarn` 直接返回 false：

| 会员 | 签到记录 | 积分流水 | 账户 |
| --- | --- | --- | --- |
| A（当天第一个） | 写入 points=5 | 有 SIGN_IN | +5 |
| B（当天第二个） | 写入 points=5 | **无** | **+0** ← bug |

**修复**：bizNo 改为 `{memberId}-{yyyyMMdd}`。

### 缺陷 3：Maven 构建缓存导致 common 修改从未生效

`~/.m2/repository` 里的 `common-messaging-1.0.0.jar` 长期停留在旧版本。
`mvn -am package` 只编译不安装，服务打包时仍从仓库取**旧 jar**：

```text
仓库 jar:      releaseClaim = true    ← 源码已改
服务内嵌 jar:   releaseClaim = false   ← 实际部署的是旧代码
```

**这意味着此前多轮针对 common-messaging 的修复都没有真正部署过。**
必须严格按顺序：`mvn install`（common）→ `mvn clean package`（各服务）→ `docker build`。

## 三、方案 A：统一进 DLQ + 定时补偿重放

### 3.1 为什么不用 `nack(requeue=true)`

实测这条路不可控：

| 问题 | 原因 |
| --- | --- |
| 无法计数 | `basicNack(requeue=true)` **不修改消息头**，`x-death` 只在经 DLX 转发时写入 |
| 无限重投 | 「第几次重试」永远读到第 1 次（实测日志连打 4 次「第 1 次」） |
| 静默丢失 | 重投耗尽后 broker 直接丢弃，队列 0、DLQ 0 |

### 3.2 现在的语义

```text
业务成功 → ack → 写幂等标记
任何失败 → 释放 Inbox 认领 → nack(requeue=false) → 经 DLX 进 xxx.dlq
                                                 ↓
                            DlqReplayScheduler（每 15s）扫描 DLQ
                              ├─ x-death.count ≤ 5 → 重放回原队列
                              └─ 超限 → 保留 + ERROR 日志，等人工
```

关键点：
- **消息永远有落点**，不会消失
- 失败时**释放 Inbox 认领**，重放才能重新认领（否则被判"已处理"跳过）
- 幂等标记只在**成功后**写入，失败不留痕迹
- 重放次数用 DLQ 的 `x-death` 如实记录，超限停止避免刷爆日志

### 3.3 涉及文件

```text
common-messaging/consumer/AbstractEventConsumer.java   统一 nack 语义 + releaseClaim
common-messaging/consumer/MessageIdempotencyGuard.java 幂等键按队列隔离
common-messaging/consumer/DlqReplayScheduler.java      新增：DLQ 补偿重放
common-messaging/inbox/ConsumerInbox.java              新增 release() 释放认领
15 个 application*.yml                                  max-attempts: 1、default-requeue-rejected: false
                                                       teaclub.messaging.dlq-queues（各服务自己的 DLQ 列表）
marketing-service/PointsServiceImpl.java               签到 bizNo 加 memberId
```

## 四、实测：失败 → DLQ → 恢复 → 重放 → 消费成功

脚本 `24-nack-redelivery.mjs`（**PASS=5 FAIL=0**）：

```text
=== 阶段1: 制造业务失败 → 消息应进 DLQ ===
  [PASS] 失败消息进入 DLQ（未丢失）  dlq.messages=1
  此时会员档案未更新（符合预期）

=== 阶段2: 恢复业务 → 补偿重放应自动消费 ===
  [PASS] 重放后消费成功  累计 0 -> 1750（应 +1750），单数 0 -> 1
  [PASS] DLQ 已清空  dlq.messages=0
  [PASS] Inbox 已记录该事件  count=1
```

幂等键格式验证（两个消费者互不干扰）：

```text
mq:consumed:teaclub.marketing.order-paid.queue:1abf93b4...
mq:consumed:teaclub.member.order-paid.queue:1abf93b4...
```

签到跨会员验证（同一天两个会员）：

```text
member=60 签到获得=5 账户总分=5
member=61 签到获得=5 账户总分=5
```

## 六、仍然存在的问题

| 项 | 说明 |
| --- | --- |
| 多实例重放并发 | `DlqReplayScheduler` 无分布式锁，多实例会重复重放（重放本身靠幂等键兜底，不会重复消费） |
| 无死信告警 | 超限消息留在 DLQ 只有 ERROR 日志，没有告警通道 |
| 重放无人工触发接口 | 目前只能等定时任务，运维无法手动催一次 |
| `order.pay-success` / `wallet.recharge-success` 队列无消费者 | 只声明不消费，消息 10 分钟 TTL 后进死信（历史遗留，与本修复无关） |

## 七、构建纪律（重要）

**改动 common-* 模块后，必须严格按此顺序：**

```bash
cd backend/teaclub-cloud
mvn -o -q clean -pl common/common-messaging
mvn -o -q -DskipTests install -pl common/common-messaging -am
mvn -o -q clean -pl <受影响服务>
mvn -o -q -DskipTests package -pl <受影响服务>
cd backend/infrastructure/docker && docker compose build <受影响服务> && docker compose up -d <受影响服务>
```

跳过 `install` 会导致服务打包时从本地仓库取**旧 jar**，改动完全不生效且无任何报错。
