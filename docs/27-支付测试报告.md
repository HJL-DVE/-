## 二、第 10–11 项的如实说明

验签、AppID 比对、商户号比对属于**真实微信支付 API v3** 的协议校验：

```text
RSA 平台证书验签    -> 需要微信平台证书与商户私钥
AES-256-GCM 解密    -> 需要 APIv3 密钥
appid / mchid 比对  -> 需要真实商户号与小程序 AppID
```

课程设计不接入真实商户，因此 `WechatPayV3Provider` 中这些方法：

- **保留了完整的方法签名与调用位置**（`verifyAndDecryptNotify` / `verifyAndDecryptRefundNotify`）
- 方法体为 `throw notImplemented(...)`，**未伪造成功**
- 切换到 `teaclub.payment.provider=wechat-v3` 时 Mock 通知接口物理上不存在（`@ConditionalOnProperty`）

> 这三项**不能声称通过**。它们需要真实商户资质才能验证。

## 三、关键设计：不把网络错误当支付失败

规格要求「不能把网络错误直接判断成支付失败」。当前实现：

```text
支付单状态机  CREATED -> PAYING -> SUCCESS / FAILED
                            ^
                            |
         只有收到明确的失败通知(CALLBACK)或主动查单确认失败，才转 FAILED
         网络超时/调用异常 -> 保持 PAYING，等待重试或主动查单
```

实测第 6 项验证：支付单在未收到任何结果时查询返回 `PAYING`，**不是 FAILED**。

---

## 四、金额校验

通知金额必须与服务端记录**逐分相等**，否则拒绝：

```java
if (notifyAmount != null && !notifyAmount.equals(payment.getAmount())) {
    throw new BizException(ResultCode.BAD_REQUEST,
        "支付金额与订单金额不一致：通知 " + notifyAmount + " 分，服务端 " + payment.getAmount() + " 分");
}
```

实测：通知 2714 分（实际 1715）被拒绝，支付单状态保持 PAYING。

## 五、幂等实现（两层）

```text
第一层  pay_payment_order 状态判断：已 SUCCESS 直接返回，不再分发业务
第二层  bizType 分发时的业务侧幂等：
        ORDER    -> order.markPaid 按订单号幂等
        RECHARGE -> wallet.processRechargePaid 按充值单号幂等
```

实测：同一支付单连续 5 次成功通知，钱包余额与流水只变动一次。
