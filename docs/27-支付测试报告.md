## 二、校验器设计

`MockNotifySignatureVerifier`（`teaclub.payment.provider=mock` 时注册）：

| 校验项 | 规则 | 配置项 |
| --- | --- | --- |
| AppID 比对 | 请求 appId 必须等于期望值 | `teaclub.payment.mock.expected-app-id` |
| 商户号比对 | 请求 mchId 必须等于期望值 | `teaclub.payment.mock.expected-mch-id` |
| 签名校验 | `SHA-256(appId\|mchId\|paymentNo\|amount\|secret)` | `teaclub.payment.mock.sign-secret` |
| 严格模式 | 三字段必须齐全，缺一即拒 | `teaclub.payment.mock.enforce-notify-check` |

### 与真实微信的差异（必须明确）

| 维度 | 真实微信 API v3 | 本项目 Mock |
| --- | --- | --- |
| 签名算法 | RSA-SHA256 + 微信平台证书验签 | SHA-256 摘要（**同构占位，无密码学强度**） |
| 报文加密 | AES-256-GCM 解密 | 明文 JSON |
| 资质来源 | 微信分配的 mchid / appid / APIv3 密钥 | 配置文件中的期望值 |
| 切换开关 | - | `teaclub.payment.provider=wechat-v3`（Mock 接口物理消失） |

> 因此本报告证明的是「**校验规则与拒绝路径正确**」，不是「真实微信联调通过」。
> 后者需要真实商户资质，本项目明确不做。

## 三、关键设计：不把网络错误当支付失败

```text
支付单状态机  CREATED -> PAYING -> SUCCESS / FAILED
                            ^
                            |
         只有明确的失败通知或主动查单确认失败，才转 FAILED
         网络超时/调用异常 -> 保持 PAYING，等待重试或主动查单
```

实测第 6 项：支付单在未收到任何结果时查询返回 `PAYING`，**不是 FAILED**。

## 四、金额校验

通知金额必须与服务端记录**逐分相等**：

```java
if (notifyAmount != null && !notifyAmount.equals(payment.getAmount())) {
    throw new BizException(ResultCode.BAD_REQUEST,
        "支付金额与订单金额不一致：通知 " + notifyAmount + " 分，服务端 " + payment.getAmount() + " 分");
}
```

实测：通知金额被篡改后拒绝，支付单状态保持 PAYING。

## 五、幂等实现（两层）

```text
第一层  pay_payment_order 状态判断：已 SUCCESS 直接返回，不再分发业务
第二层  业务侧幂等：
        ORDER    -> order.markPaid 按订单号幂等
        RECHARGE -> wallet.processRechargePaid 按充值单号幂等
```

实测：同一支付单连续 5 次成功通知，钱包余额与流水只变动一次。
