## 一、总体原则

```text
1. 数据库归属唯一：每个库只有一个服务可写，禁止跨库直改
2. 跨服务一致性：本地事务 + Outbox + Saga 补偿，不用两阶段提交
3. 资金正确性：数据库行锁/唯一索引为主，Redis 锁只做性能优化
4. 失败可恢复：任何中间态都必须有明确的推进或补偿路径
```

**验证**：order-service 与 payment-service 对 `wal_wallet` / `wal_wallet_transaction` **零引用**
（grep 全代码库确认），资金变动只能经由 wallet-service 的内部接口。

## 二、Transactional Outbox（事务发件箱）

### 2.1 表结构

```sql
sys_outbox_message(
  event_id    PK,          -- 全局唯一，消费端幂等键
  event_type, biz_no, routing_key, payload,
  version, trace_id, occurred_at,
  status,                  -- PENDING / SENT / FAILED
  attempts, last_error, created_at
)
```

### 2.2 工作方式

```text
业务事务内：  INSERT 业务数据  +  INSERT outbox(status=PENDING)   <- 同一本地事务
提交成功后：  OutboxRelay 定时(1s)扫描 PENDING/FAILED -> 投递 RabbitMQ -> 标记 SENT
投递失败：    status=FAILED, attempts+1，下次扫描重试
```

### 2.3 消息投递确认

```text
RabbitMQ 投递返回成功后 才 标记 SENT。
若进程在「投递成功」与「标记 SENT」之间崩溃 -> 重启后重复投递。
这是刻意的「至少一次」语义，由消费端 Inbox 幂等消化。
```

**实测**：登记 `ORDER_PAID` 事件 -> 3 秒后 pending=0 -> 数据库 `status=SENT`。

## 三、Consumer Inbox（消费收件箱）

### 3.1 双层幂等

```text
第一层 Redis   mq:consumed:{eventId}  SETNX TTL 72h    高速筛子
第二层 DB      sys_inbox_message(event_id PK)            最终防线
```

### 3.2 处理顺序

```text
收到消息 -> Redis 占位 -> DB 插入 event_id -> 执行业务
          失败即丢        主键冲突即丢        业务自身还需幂等
```

> 关键认知：Inbox 只保证「同一条消息不重复处理」，
> **不能**替代业务自身的幂等键（如 `uk_txn_biz`）。
> 资金幂等最终由钱包唯一索引保证。

## 四、消息重试与死信

```text
消费失败 -> MessageRetryPolicy 本地重试（次数有限）
         -> 重试耗尽 -> 投递 DLX_EXCHANGE -> 死信队列 DLQ
         -> 人工/补偿任务介入
```

死信队列命名：`{原队列}.dlq`，与业务队列一一对应。

## 五、Saga 状态机（余额支付）

这是本任务新增的核心组件，用于彻底消除「钱扣了但订单永久待支付」。

### 5.1 状态定义

| step | status | 含义 |
| --- | --- | --- |
| DEDUCTING | RUNNING | 已登记，尚未调用钱包扣款 |
| DEDUCTED | RUNNING | 钱包已扣款成功，订单尚未更新 |
| ORDER_PAID | COMPLETED | 订单已更新，Saga 完成 |
| COMPENSATED | COMPENSATED | 已回冲，资金退回会员 |
| - | FAILED | 补偿失败，待补偿任务重试或人工介入 |

### 5.2 为什么必须用 REQUIRES_NEW

```text
Saga 记录若与业务同事务 -> 业务回滚时 Saga 记录一起消失
-> 补偿任务看不到孤儿扣款 -> 钱永久丢失

因此 PaymentSagaService 的所有写方法使用 Propagation.REQUIRES_NEW，
确保 Saga 记录独立提交，外层回滚后依然存在。
```

### 5.3 执行流程

```text
1. begin()        INSERT oms_payment_saga(DEDUCTING, RUNNING)   [独立事务]
2. walletClient.consumeOut(...)                                   [远程扣款]
3. markDeducted() UPDATE step=DEDUCTED                          [独立事务]
4. orderMapper.updateById(PAID)                                   [本地事务]
5. markCompleted() UPDATE step=ORDER_PAID, status=COMPLETED     [独立事务]

第 4 步抛异常 -> catch 中调用 walletClient.refundIn(COMP-订单号)
              -> markCompensated()  资金立即退回
              -> 重新抛出异常，接口返回失败，订单保持 UNPAID
```

### 5.4 实测结果

```text
正常支付  -> Saga 记录 ORDER_PAID / COMPLETED
滞留补偿  -> 手工构造 DEDUCTED/RUNNING（300 秒前）
           补偿任务 30 秒内自动回冲
           Saga -> COMPENSATED，余额 44210 -> 45925（+1715）
```

## 六、补偿任务

| 任务 | 周期 | 职责 |
| --- | --- | --- |
| `OutboxRelay` | 1s | 投递未发送的领域事件 |
| `PaymentSagaCompensator` | 30s | 扫描滞留 Saga，订单未支付则回冲资金 |
| `FreezeExpiryScheduler` | 10s | 释放过期冻结（确认超时） |
| `PaymentTimeoutCloser` | 60s | 关闭超时支付单（CREATED/PAYING → CLOSED） |
| `WalletReconciliationService` | 10min | 库内资金对账 I1–I6 |
| `OrderWalletReconciliationService` | 15min | 订单 ↔ 钱包跨服务对账 |

所有补偿动作**幂等**：

```text
回冲使用固定单号 COMP-{订单号}，重复执行只入账一次
冻结释放使用条件更新 WHERE status='FROZEN'，并发安全
```

### 事件接入点（已在业务方法内实现）

| 服务 | 触发点 | 事件 |
| --- | --- | --- |
| order | 余额支付成功 | ORDER_PAID |
| order | 微信支付回写已支付 | ORDER_PAID |
| wallet | 充值入账 | RECHARGE_PAID |
| wallet | 消费扣款 / 冻结确认扣款 | WALLET_DEDUCTED |
| wallet | 冻结余额 | WALLET_FROZEN |
| payment | 支付成功 | PAYMENT_SUCCEEDED |
| payment | 退款成功 | REFUND_SUCCEEDED |

各服务用自己的 `sys_outbox_message` 表承载，与业务库同库同事务。

## 七、异常订单扫描

`PaymentSagaCompensator` 同时承担异常订单扫描职责：

```text
扫描条件： status=RUNNING AND step IN (DEDUCTING, DEDUCTED)
          AND update_time < NOW() - 60s

处理分支：
  订单不存在        -> markFailed，人工介入
  订单已 PAID       -> markCompleted（只是 Saga 状态没跟上）
  订单未 PAID       -> 回冲资金 -> markCompensated
  回冲失败          -> markFailed，下轮重试
```

## 八、定期对账

`WalletReconciliationService` 独立校验资金不变量，不依赖业务代码自证：

| 编号 | 不变量 | 校验 SQL 要点 |
| --- | --- | --- |
| I1 | 余额非负 | `principal_balance < 0 OR gift_balance < 0` |
| I2 | 余额守恒 | 余额 == SUM(流水变动) |
| I3 | 单笔自洽 | `after == before + change` |
| I4 | 链式衔接 | `LAG(after)` == 本条 `before` |
| I5 | 业务唯一 | `(biz_type, biz_no)` 不得重复 |
| I6 | 冻结可控 | 有效冻结额 <= 账户余额 |

**实测**：`passed=true`, `wallets=8`, `ledgers=45`, `issues=0`。

## 九、各跨服务流程的状态与补偿

| 流程 | 成功 | 失败 | 中间态 | 补偿方式 |
| --- | --- | --- | --- | --- |
| 充值 | 充值单 PAID + 钱包入账 | 充值单保持 PENDING | 支付中 PAYING | 重复通知幂等；超时支付单需人工/关单 |
| 余额消费 | 订单 PAID + 钱包扣款 | 订单 UNPAID + 无扣款 | Saga DEDUCTED | 立即回冲 + 定时补偿 |
| 微信支付 | 支付单 SUCCESS + 订单 PAID | 支付单 FAILED | PAYING | 主动查单对齐 |
| 退款 | 退款单 SUCCESS + 订单 REFUNDED | 退款单 FAILED | PROCESSING | 可重新申请（FAILED 不计入占用） |
