## 1. 十五条硬性要求与验证方式

每条要求都必须有**可执行的验证方式**，不接受"我认为符合"这类主观判断。

| # | 要求 | 本项目执行方式 | 验证手段 |
| --- | --- | --- | --- |
| 1 | 不允许只创建文件/空类宣称完成 | 每个 Service 必须实现接口全部方法，且方法体有真实逻辑 | 空方法体扫描 + 真实调用接口验证 |
| 2 | 不允许硬编码数据冒充真实接口 | 所有数据来自 MySQL 查询；种子数据仅作初始化 | 接口返回随数据库变化而变化 |
| 3 | 不允许删除功能解决编译错误 | 修复而非移除 | 功能清单回归测试 |
| 4 | 不允许绕过权限校验 | 写操作必须有权限点；门店数据必须过 StoreScope | 越权攻击测试脚本 |

## 2. 汇报模板（强制）

每次汇报固定包含以下六节，缺一不可：

```text
一、本次完成的功能
二、修改或新增的文件
三、测试及编译结果
四、当前存在的问题
五、下一步计划
六、需要用户提供的外部配置或资料
```

**禁止表述**：

- 未实际运行不说"已运行成功"
- 未联调不说"微信支付已接入"
- 容器未拉起不说"Docker 部署已完成"
- "编译通过"不等于"功能验证通过"

## 3. 完成度分级定义

避免"完成"含义模糊，统一使用四级：

| 级别 | 含义 | 判定标准 |
| --- | --- | --- |
| **已验证** | 真实运行并断言通过 | 有测试执行记录 + 断言数量 |
| **已实现未验证** | 代码写完但未运行 | 明确标注"未运行" |
| **仅设计** | 只有文档/接口定义 | 无代码 |
| **未开始** | 无任何产物 | — |

### U-09 决策记录（已确认为 B 方案）

> **2026 决策：选择 B**。原因为连锁品牌统一会员场景下，
> 会员跨店消费时收银台必须能识别其身份，否则出现"看得到订单却查不到会员"的矛盾。
>
> 实现位置：
> - `MemMemberMapper.selectVisibleMemberIds` —— 统一可见性 SQL
> - `MemMemberServiceImpl.page / findByPhone / assertMemberVisible`
> - `WalletQueryServiceImpl.pageWallet / getByMember`
>
> 验证：`scripts/member-visibility-test.mjs`（12 项断言全通过）

### 原 U-09 方案对比（保留存档）

当前门店角色查询会员时，过滤条件是：

```sql
mem_member.register_store_id IN (该员工被授权的门店集合)
```

含义：**会员在 A 店注册，则 B 店员工查不到该会员**，即使该会员在 B 店消费过。

- 优点：会员画像不外泄，隐私边界清晰
- 缺点：B 店收银台无法服务"在 A 店注册、但到 B 店消费"的会员

**替代口径**（若希望 B 店能服务该会员）：

```sql
-- 可见条件改为：注册门店在授权范围 OR 在本店有消费记录
WHERE register_store_id IN (...)
   OR id IN (SELECT member_id FROM oms_order WHERE store_id IN (...))
```

该方案依赖订单表，需在订单模块建表后才能实现。**进入订单模块前需要你确认采用哪种口径。**

## 7. 客户端金额字段的显式澄清（对应第 6 条 / 第 14 条）

第 6 条要求"不允许通过前端传入金额决定实际支付金额"。经代码审计，系统中有
**两处业务流程必然涉及客户端传入金额**，特此显式记录其约束，避免被误判为违规。

### 7.1 自定义充值金额 `RechargeCreateRequest.customAmount`

**为什么需要**：需求文档 D-03 明确要求"自定义充值金额"功能，会员可自行输入充值数额。

**约束（代码实现）**：

```java
// RechargeServiceImpl.createRecharge
if (Objects.equals(plan.getCustomAmountEnabled(), 1)) {
    rechargeAmount = request.getCustomAmount();     // 仅自定义方案接受
    validateCustomAmount(plan, rechargeAmount);     // 必须落在方案区间内
    giftAmount = 0L;                                 // 自定义方案不赠送
} else {
    rechargeAmount = plan.getRechargeAmount();       // 固定方案：服务端决定
    giftAmount = plan.getGiftAmount();               // 赠送额：服务端决定
}
```

| 保护点 | 说明 |
| --- | --- |
| 仅自定义方案接受 | 固定方案完全忽略客户端金额 |
| 上下限校验 | `min_custom_amount` ≤ amount ≤ `max_custom_amount`，越界拒绝 |
| 赠送额不受影响 | 自定义方案赠送额恒为 0，客户端无法通过金额撬动赠送 |
| 方案可用性校验 | 时间窗口、参与门店、会员等级、每人次数全部服务端校验 |

**结论**：客户端只能决定"充多少"，无法决定"送多少"或"到账多少"。充值单落库金额即服务端校验后的值，支付通知金额还需与之逐分比对。

### 7.2 退款金额 `RefundApplyRequest.refundAmount`

**为什么需要**：部分退款场景下，操作员需指定退多少（如只退一杯）。

**约束（代码实现）**：

```java
// PaymentServiceImpl.applyRefund
long paid     = order.getPaidAmount();
long refunded = order.getRefundedAmount();
long refundable = paid - refunded;
if (request.getRefundAmount() > refundable) {
    throw new BizException("退款金额超过可退余额：可退 " + refundable + " 分");
}
// 资金构成由服务端按原扣款比例分摊，客户端无法指定实付/赠送各退多少
long[] alloc = allocateRefund(origPrincipal, origGift, paid, request.getRefundAmount());
```

| 保护点 | 说明 |
| --- | --- |
| 上限硬校验 | 不得超过 `实付 - 已退` |
| 构成由服务端定 | 实付/赠送如何分摊，客户端无权指定 |
| 幂等 | 退款单号唯一，并发退款只成功一次（实测 5 并发 → 1 成功） |
| 原路返回 | 余额支付回冲钱包，微信支付走渠道，不可交叉 |

**结论**：客户端只能决定"退多少（不超上限）"，无法决定"退到哪里""按什么构成退"。

### 7.3 明确不允许的场景（已通过代码杜绝）

| 场景 | 状态 |
| --- | --- |
| 下单传入商品单价 / 总价 | ❌ `OrderItemRequest` 只有 `skuId` + `quantity` |
| 支付传入支付金额 | ❌ `PayCreateRequest` 只有 `bizNo` + `bizType` |

| 前端回调即认定支付成功 | ❌ 只认服务端通知/查单 |
