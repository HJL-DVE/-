## 二、发现的真实缺陷与修复

### 2.1 缺陷现象

严格验证时发现：**同一订单可以连续申请两次全额退款**。

```text
第1次全额退款 -> code=0  refundNo=RF...026  status=PROCESSING
第2次全额退款 -> code=0  refundNo=RF...027  status=PROCESSING   <- 不应成功
订单已退金额 = 0                                                <- 未回写
```

### 2.2 根因

可退金额判定读取的是 `order_db.oms_order.refunded_amount`，而该字段**只在退款成功通知时才更新**。
微信退款是异步的：申请后状态为 `PROCESSING`，在收到平台成功通知前 `refunded_amount` 一直是 0。
因此第二次申请仍然通过 `refundable = paid - 0 = 1715` 的校验。

### 2.3 修复

把「已占用退款额」的权威来源从 order_db 改为 **payment_db 本地的退款单表**：

```sql
SELECT COALESCE(SUM(refund_amount),0) FROM pay_refund_order
WHERE biz_no = #{bizNo} AND biz_type = 'ORDER'
  AND status NOT IN ('FAILED','CANCELLED')
```

为什么这样是对的：

| 维度 | 说明 |
| --- | --- |
| 事务一致 | 退款单插入与可退金额校验在同一个本地事务（同一个库），不存在跨库时序问题 |
| 幂等 | 第二次申请时第一条退款单已存在，SUM 立即包含它，校验直接拦截 |
| 可恢复 | 排除 FAILED/CANCELLED，失败退款可以重新申请 |
| 无需远程调用 | 不依赖 order-service 可用性，减少故障面 |

### 2.4 修复后验证

```text
第1次全额退款 -> code=0  status=PROCESSING
第2次全额退款 -> code=10002「该订单已无可退金额（实付 1715 分，已占用退款 1715 分）」
```

## 三、退款与原始凭证的关联

规格要求「退款必须关联原始支付单和原始资金流水」。当前实现：

```text
pay_refund_order.payment_no  -> 原支付单号 pay_payment_order.payment_no
                               （余额支付无支付单时，用 BAL-订单号 合成可追溯引用）
pay_refund_order.biz_no      -> 原订单号 oms_order.order_no
wallet 退款流水 biz_no        -> 退款单号，可反查 refundNo
```

余额退款时按**原扣款构成**分摊：`balance_principal_amount` / `balance_gift_amount` 决定实付与赠送各退多少。

## 四、关键时序：退款成功只在平台确认后

实测验证：

```text
申请退款 -> 退款单 PROCESSING，订单保持 PAID   <- 不提前置为已退
平台确认 -> 退款单 SUCCESS ，订单转 REFUNDED
```

这符合规格「退款成功只有在平台确认后」。
