## 1. 项目概述

TeaClub 是一套面向连锁奶茶店的会员与储值营销管理系统，采用微服务架构实现。系统覆盖会员管理、商品管理、储值钱包、订单交易、模拟支付、营销活动、经营报表七大业务域，提供 Vue 3 管理后台（总部/店长/收银员三种角色）与微信小程序（会员端）。

核心业务能力：

- **会员储值**：充值套餐（充 X 送 Y）、钱包本金/赠送分账管理、余额支付、冻结-解冻资金模型；
- **订单交易**：小程序点单、服务端试算、优惠券抵扣、钱包/模拟微信双支付通道、退款冲正；
- **营销体系**：优惠券（8 类模板）、积分（账户/流水/批次/签到/商城）、会员等级（5 级、消费自动升级）、营销活动（8 类，事件驱动自动发奖）；
- **经营报表**：总部/门店驾驶舱、销售趋势、商品排行、会员增长、储值支付退款统计。

系统规模（真实统计）：

- 微服务 9 个（含网关）；数据库 9 个；业务数据表 63 张；
- 回归测试 19 个脚本、246 项断言全部通过；
- 全链路真实可用：注册 → 充值 → 下单 → 支付 → 积分 → 报表五方数据一致。

启动方式：后端/前端可在 IDEA / VSCode 中直接启动（本课程设计演示方式），也可使用 Docker Compose 一键部署（见 docs/DEPLOYMENT.md）。

## 2. 项目背景及意义

### 2.1 背景

连锁奶茶门店普遍存在三类痛点：一是会员分散在各门店，总部无法统一运营；二是储值（充值赠送）资金涉及预收款，管理不规范易引发资金纠纷；三是营销活动（优惠券、积分、等级）依赖人工，无法数据化度量效果。

### 2.2 意义

本项目以微服务架构实现统一的会员储值营销平台：

- 会员与资金集中管理，总部统一视图，门店按权限访问；
- 储值资金「本金/赠送」双账本 + 每笔流水链式记录，账实相符可审计；
- 营销活动配置化，发奖由订单事件自动驱动，效果可量化（报表域）；
- 微服务拆分使各业务域独立迭代、独立部署，符合真实企业架构演进路径。

### 2.3 课程设计目标

本课程设计综合运用 Java 后端、分布式系统、数据库设计与前端工程知识，重点训练：微服务拆分能力、分布式事务处理（Outbox/Saga）、消息可靠性投递、资金一致性设计、多角色权限体系，以及前后端全栈协作。

## 3. 系统需求分析

### 3.1 功能需求（按角色）

| 角色 | 需求 |
| --- | --- |
| 总部管理员 | 门店/员工/角色权限管理；商品与套餐管理；全量会员、订单、流水视图；营销活动配置；经营报表 |
| 店长 | 本店数据范围下的会员/订单/报表；本店营销活动查看 |
| 收银员 | 门店收银工作台（点单、收款）；无财务报表与系统管理权限 |
| 会员（小程序） | 注册登录、浏览点单、钱包充值与余额支付、领券用券、积分签到、参与活动、兑换商城 |

### 3.2 非功能需求

| 类别 | 要求 | 实现情况 |
| --- | --- | --- |
| 资金安全 | 余额不得为负；重复充值/退款不重复入账；金额服务端计算 | ✅ 条件 UPDATE + 唯一索引 + Inbox 幂等 |
| 消息可靠 | 业务与消息原子性；失败不丢消息 | ✅ Outbox 模式 + DLQ + 定时补偿重放 |
| 数据权限 | 店长仅本店、收银员无财务 | ✅ 后端逐接口校验 storeIds |
| 可用性 | 服务宕机不丢消息，恢复后继续消费 | ✅ RabbitMQ 持久化 + 手动 ack |

### 3.3 范围裁剪（课程设计明确不做）

真实微信支付（Mock 替代）、库存管理、Kubernetes、监控平台、CI/CD。

## 7. 微服务设计

| 服务 | 端口 | 数据库 | 职责 | 关键点 |
| --- | --- | --- | --- | --- |
| auth-service | 9001 | iam_db | 用户/角色/权限/门店/品牌，签发 JWT | 双令牌（管理端/会员端）密钥隔离 |
| member-service | 9002 | member_db | 会员档案/等级/微信绑定/消费统计 | 消费事件驱动等级自动升级 |
| product-service | 9003 | product_db | SPU/SKU/分类/门店商品 | 图片 OSS 存储 |
| wallet-service | 9004 | wallet_db | 钱包/充值套餐/流水/冻结 | 本金/赠送双账本、条件 UPDATE 防超扣 |
| order-service | 9005 | order_db | 订单/试算/状态机/Saga | 金额服务端重算、Outbox 发事件 |
| payment-service | 9006 | payment_db | 支付单/退款单/Mock 渠道 | Mock 签名校验、回调幂等 |
| marketing-service | 9007 | marketing_db | 券/积分/等级权益/活动 | REQUIRES_NEW 发奖、事件消费 |
| report-service | 9008 | report_db | 经营报表只读聚合 | 跨库 SELECT-only 账号 |
| gateway-service | 9000 | — | 路由/JWT/白名单 | 转发用户身份头 |

服务间通信：同步 OpenFeign（查商品/会员/钱包），异步 RabbitMQ（ORDER_PAID、REFUND_SUCCEEDED）。

### 7.1 消息拓扑

- 交换机 teaclub.business.exchange（生产方 outbox 定时投递）；
- 队列：member.order-paid、marketing.order-paid、marketing.refund-success 等，每队列配 DLQ；
- 消费失败 → nack(requeue=false) → DLQ → DlqReplayScheduler 每 15s 重放（≤5 次）；
- 幂等三层：Redis 预筛（键含队列名）→ DB Inbox（与业务同事务）→ 业务唯一索引。

## 9. 会员管理设计

- 注册：小程序 wx-login（mock code2session）静默注册，占位手机号为 1 开头 11 位数字（openid SHA-256 派生，同号稳定）；管理端可手工建会员；
- 等级：mem_member_level 5 级（普通→银卡→金卡→黑金→钻石），upgrade_type=CONSUME_AMOUNT，门槛 0/500/1500/5000/12000 元；消费档案更新后自动重算（只升不降）；
- 权益：mkt_level_benefit 按等级配置积分倍率/生日券/生日积分/专属券/优先服务，积分发放时按倍率实算（如金卡 1.5 倍：17.5元→24分）。

## 10. 储值与充值业务设计

### 10.1 双账本

- wal_wallet.principal_balance（本金）/ gift_balance（赠送）分列；
- 充 100 送 20：本金 +10000 分、赠送 +2000 分，到账 120 元；赠送不计收款；
- 赠送可设有效期（gift_expire_days），由营销服务批次过期任务处理。

### 10.2 资金安全四道防线

1. 条件 UPDATE：SET balance=balance-? WHERE balance>=?（防超扣/超发）；
2. 唯一索引：uk_txn_biz(biz_type,biz_no) 防重复入账/退款；
3. 链式流水：每笔记录 before/change/after，逐笔可审计（I3/I4 不变量）；
4. 冻结模型：下单先冻结后扣减（wal_wallet_freeze），取消解冻。

## 11. 订单管理设计

- 状态机：UNPAID → PAID → COMPLETED /（CANCELLED、REFUNDING、REFUNDED）；
- 金额全部服务端重算：商品额 → 活动折扣 → 等级折扣 → 券抵扣 → 应付；券抵扣走 marketing 内部接口试算，下单锁券、支付核销、取消释放；
- 支付成功：Saga 完成记录 + Outbox 写 ORDER_PAID 事件（与业务同事务）。

## 12. Mock 支付设计

- teaclub.payment.provider=mock 时注册 MockPaymentController；
- create → PAYING；POST /mock/notify → SUCCESS（金额不符/签名不符拒绝）；
- POST /mock/fail 模拟失败；重复通知幂等（状态机拒绝二次变更）；
- 前端明确标注「模拟支付数据，非真实收款」。

---

## 13. 会员营销设计

- 优惠券：模板（8 类）→ 领取（Redis 800ms 锁+限领）→ 锁定（UNUSED→LOCKED）→ 核销（→USED）→ 释放（订单取消）；
- 积分：账户/流水（唯一索引防重）/批次（有效期）；消费得积分（等级倍率）、签到、活动奖励、兑换扣减、退款冲正（按原流水额）；
- 活动：8 类，FULL_GIFT/STORE_SPECIAL 由 ORDER_PAID 事件自动触发，参与记录唯一键防重，发券 REQUIRES_NEW 独立事务；
- 等级权益：POINT_RATE 倍率真实应用于积分发放。

## 14. 经营报表设计

- report-service（9008）：跨库 SELECT-only 聚合（不改动 7 个业务服务）；
- 11 个 GET 接口：总部/门店驾驶舱、趋势（补零）、排行、增长、储值/支付/退款/营销分析；
- 口径：销售=订单实付；充值=本金（赠送单列）；模拟支付标注 mockPaymentMark；钱包消费单列不重复计收；
- 权限：总部全量、店长限本店（越权 10202）、收银员无权限（10201）。

## 18. 项目总结与展望

### 18.1 收获

- 完整走通微服务拆分：按业务域分库分服务、Feign 同步 + MQ 异步协同；
- 资金一致性实践：Outbox、Saga 补偿、条件 UPDATE、链式流水、幂等三层；
- 真实问题排查：Maven 缓存致改动未部署、消息幂等键未隔离、发奖事务污染等 8+ 个真实缺陷的定位与修复；
- 前后端全栈：Vue 管理后台 28 页、小程序 26 页。

### 18.2 不足与展望

| 不足 | 展望 |
| --- | --- |
| 微信支付为 Mock | 接入真实商户号与回调验签 |
| 操作日志未接入新操作 AOP | 统一操作审计切面 |
| 部分活动触发（生日/沉睡召回）未接定时任务 | 定时扫描 + 事件驱动 |
| 无监控告警 | Prometheus + Grafana、DLQ 告警 |
| 报表为实时聚合 | 数仓/物化视图支撑大规模数据 |
| 4 类活动无自动触发入口 | 注册/生日/沉睡事件接入 |
