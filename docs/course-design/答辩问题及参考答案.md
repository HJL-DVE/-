# TeaClub 答辩问题及参考答案（共 30 题）

> 基于项目真实实现整理。标注★的是高频问题，务必熟练。

---

## 一、架构类

### ★1. 为什么使用 Spring Cloud？为什么使用微服务？

**答**：单体架构在业务扩张时会出现模块耦合、部署牵一发动全身、团队协作冲突等问题。本项目有会员、钱包、订单、支付、营销等 7 个业务域，资金与营销逻辑差异大、变更频率不同，拆分为微服务后：
- 每个服务独立数据库、独立部署，改营销不影响支付；
- 故障隔离：营销服务挂了不影响钱包扣款；
- 按服务独立扩容（如订单服务压力大可单独加实例）。
Spring Cloud 提供了微服务落地的全家桶：Nacos 做注册配置、Gateway 做统一入口、OpenFeign 做服务间调用、Sentinel 可做限流，避免重复造轮子。

### ★2. Gateway 的作用是什么？

**答**：系统唯一入口（9000 端口），职责：
1. **统一路由**：按路径（/api/member/** 等）转发到对应服务，前端只认识一个地址；
2. **统一鉴权**：解析 JWT，校验通过后把用户身份（userId、roles、storeIds 等）放入请求头转发给下游，下游服务无需重复解析令牌；
3. **白名单**：登录、Mock 回调等免认证路径统一配置；
4. **负载均衡**：lb:// 协议结合 Nacos 服务发现自动分配实例。
它是 WebFlux 响应式编程（不含 feign-core，避免误装配 Servlet 栈组件）。

### ★3. Nacos 的作用是什么？

**答**：两个作用。
1. **服务注册与发现**：8 个服务启动时注册到 Nacos，Gateway 通过 lb:// 按服务名负载均衡调用，无需硬编码 IP；
2. **配置中心**：统一管理配置（如数据库连接），支持动态刷新。
项目按 TEACLUB 分组隔离，避免多套环境冲突。

### ★4. OpenFeign 如何调用其他服务？

**答**：声明式 HTTP 客户端。定义接口加 @FeignClient(name="member-service")，方法上加 @GetMapping 等注解，调用时像调本地方法一样。底层流程：接口代理 → 结合 Nacos 服务发现拿到实例地址 → Ribbion/LoadBalancer 负载均衡 → 发 HTTP 请求 → 结果反序列化。
关键细节：项目通过 FeignRequestInterceptor 拦截器统一注入**内部令牌 X-Internal-Token** 与用户身份头（X-User-Id、X-Store-Ids），下游服务据此做鉴权与数据范围过滤；还统一配置了超时、重试、异常解码。

### ★5. RabbitMQ 有什么作用？

**答**：实现服务间**异步解耦**与**最终一致性**。以「订单支付成功」为例：order-service 落库订单后在**同一本地事务**写一条 Outbox 事件（ORDER_PAID），定时任务投递到 RabbitMQ；member-service（更新消费档案、等级升级）与 marketing-service（发积分、满赠活动）各自消费，互不影响主流程。好处：
- 支付主流程不被下游拖慢；
- 消费者宕机消息不丢（持久化 + 手动 ack）；
- 新增订阅方（如报表）无需改生产方。
失败处理：消费失败 nack 进 DLQ，DlqReplayScheduler 每 15 秒重放最多 5 次，超限留 DLQ 待人工。

## 二、资金与钱包类

### ★6. 如何设计会员钱包？

**答**：wal_wallet 一人一钱包，两个余额字段：**principal_balance（本金）**与 **gift_balance（赠送）**，分开记账。扣款顺序可配置（先赠后本 GIFT_FIRST / 先本后赠）。每笔变动写 wal_wallet_transaction 链式流水（before/change/after），逐笔可审计。充值、消费、退款、冻结（下单预占）都产生流水。

### ★7. 如何处理充值赠送？

**答**：充值套餐（wal_recharge_plan）定义 recharge_amount（本金）与 gift_amount（赠送）。充 100 送 20：本金 +10000 分、赠送 +2000 分，**钱包到账 120 元，但收款只认 100 元**——赠送不算收款，报表里赠送单列并标注。赠送可设有效期（gift_expire_days），到期由批次任务扣减。这个口径在报表接口里通过 giftNotCountedAsPayment=true 显式声明。

### ★8. 如何避免重复充值？

**答**：三层防线。
1. **支付单状态机**：PAYING → SUCCESS 单向流转，已 SUCCESS 再收通知直接拒绝（实测）；
2. **唯一索引**：uk_txn_biz(biz_type, biz_no)，同一业务单只允许一条入账流水，重复回调触发唯一键冲突被幂等忽略；
3. **消费端 Inbox**：事件消费先写 sys_inbox_message（与业务同事务），重复投递直接跳过。
实测：对同一支付单重复发 mock/notify，余额不变。

### ★9. 资金安全还做了哪些设计？

**答**：
1. **条件 UPDATE 防超扣**：UPDATE ... SET balance=balance-? WHERE balance>=?，并发下不会扣成负数；
2. **链式流水**：每笔记录 before/change/after，I3 不变量校验 after=before+change；
3. **冻结模型**：下单先冻结（wal_wallet_freeze），支付成功扣减、取消解冻，避免超卖；
4. **金额服务端计算**：前端传商品和数量，金额全部由后端试算与重算，客户端无法篡改；
5. **对账**：余额 = 流水累计（I2 不变量），异常可发现。

## 三、支付类

### ★10. Mock 支付是如何实现的？

**答**：通过配置开关 teaclub.payment.provider=mock 条件注册 MockPaymentController（真实环境注册真实渠道实现，同一接口）。流程：
1. create 创建支付单（PAYING），返回 paymentNo；
2. 调 POST /api/payment/mock/notify 模拟微信回调，先经 MockNotifySignatureVerifier 验签（SHA-256 同构占位实现，模拟真实微信的 appId/mchId/sign 三要素校验）；
3. 校验通过且金额一致才置 SUCCESS，触发下游入账。
保留真实支付的**验签、幂等、状态机**逻辑，只是把「微信服务器」换成了本地模拟。前端界面明确标注「模拟支付数据，非真实收款」。

### 11. 支付回调如何保证幂等？

**答**：支付单状态机单向流转（PAYING→SUCCESS），已 SUCCESS 的单再收通知直接返回成功但不重复入账；业务入账侧靠 uk_txn_biz 唯一索引兜底。实测对同一支付单重复 notify，钱包余额不变。

### 12. 退款如何防止重复退款？

**答**：同上。退款单有独立状态机（PENDING→SUCCESS），重复回调被拒；退款冲正流水有唯一索引；实测重复退款回调后积分冲正流水仍为 1 条。

## 四、营销类

### ★13. 如何设计会员积分？

**答**：三张表。mkt_points_account（账户余额）、mkt_points_transaction（流水，唯一索引 uk_points_biz 防重）、mkt_points_batch（批次，含有效期，供过期扣减）。来源：消费得积分（按等级倍率）、签到、活动奖励；消耗：积分商城兑换；冲正：退款按原消费流水额反向冲减（不重新计算）。

### 14. 如何实现会员等级自动升级？

**答**：等级表定义 upgrade_type=CONSUME_AMOUNT 与 upgrade_threshold。消费后（ORDER_PAID 事件）在会员服务重算：查累计消费命中的最高等级，若高于当前等级则更新（只升不降）。实测：新会员消费 507 元后自动从普通升为银卡，等级权益（1.2 倍积分）同步生效。

### ★15. 优惠券是如何设计的？

**答**：模板与实例分离。mkt_coupon_template 定义规则（类型：满减/折扣/无门槛/兑换/新人/生日等；面额/门槛/有效期/范围：门店/商品/等级/总量/限领）；领取时生成 mkt_coupon 实例（冗余面额快照，防止改模板影响已发券）。使用走状态机 UNUSED→LOCKED（下单锁券）→USED（支付核销）→UNUSED（取消释放）。抵扣金额由 marketing 服务试算接口判定，订单服务不自行计算。

### 16. 优惠券如何保证不被重复使用？

**答**：条件 UPDATE（SET status='USED' WHERE status='LOCKED' AND order_no=?）+ 状态机拒绝非法流转 + 券号唯一。并发下两个订单同时锁同一张券，只有一个能成功。

### 17. 满减、折扣、兑换券的计算逻辑有何不同？

**答**：满减：满 threshold 减 face_value；折扣：按 discountRate（万分数）乘订单额，可设 maxDiscountAmount 封顶；兑换：凭券换指定 SPU/SKU。全部在 marketing-service 的 calculateDiscount 中实现，order-service 只拿结果。

## 五、权限与报表类

### ★18. 如何实现多门店权限？

**答**：三处配合。
1. sys_user_store 表绑定用户与门店；
2. JWT 中携带 allStoreAccess 与 storeIds，Gateway 转发；
3. 业务服务用 StoreScope 校验：总部（allStoreAccess=true）看全部；店长只能访问 storeIds 中的门店，传未授权的 storeId 直接抛 10202「没有门店[2]的数据权限」。
实测：店长访问门店 2 数据被拒，收银员无报表权限返回 10201。

### ★19. 经营报表如何统计？

**答**：report-service 独立服务，通过**跨库只读账号**（tc_report，仅有各业务库 SELECT 权限）直接聚合查询，不改动 7 个业务服务、不引入数仓。特点：
1. 口径严格：销售=订单实付；充值=本金（赠送单列不计收款）；模拟支付单独标注；钱包消费不重复计入收款；
2. 趋势图缺失日期补零，前端折线不断点；
3. 商品排行 metric 参数白名单校验防 SQL 注入；
4. 门店/日期筛选在 SQL 层完成，权限（店长仅本店）在 WHERE 条件内强制。
说明：课程设计采用跨库只读简化方案；生产化可演进为各服务提供统计接口 + Feign 聚合，或走数仓。

### 20. 报表为什么用跨库只读而不是 Feign 聚合？

**答**：如实回答——两种方案都实现了接口设计。当前采用跨库只读（tc_report 账号仅 SELECT 权限）是因为 7 个业务服务原本没有趋势/排行类统计接口，改造它们会引入变更风险；跨库只读是课程设计阶段的务实选择，且不破坏「服务数据私有」原则（只读、独立账号、无写操作）。FeignClient 已预留，后续服务补统计接口可平滑切换。

## 六、工程与测试类

### 21. Outbox 模式是什么？为什么需要？

**答**：解决「业务落库成功但发消息失败」的不一致。做法：业务数据与事件在**同一个本地事务**写入 outbox 表，定时任务异步投递到 MQ。保证要么都成功、要么都不发，配合消费端幂等实现最终一致性。

### 22. 消息消费失败怎么办？

**答**：手动 ack 模式下，消费失败 nack(requeue=false) 进入死信队列 DLQ（不丢失）；DlqReplayScheduler 每 15 秒扫描 DLQ，按 x-death 次数重放（≤5 次），超限保留待人工。幂等由 Redis+Inbox+唯一索引三层保证，重放不会重复消费。

### 23. 项目遇到过的最难的问题是什么？（展示排查能力）

**答**：举真实案例——「会员消费后等级不升级」。排查发现系统根本没有升级逻辑（只有消费累计）；补上后仍未生效，继续排查发现是测试脚本时间用了 UTC 导致活动被判定过期；再排查发现活动发奖事务被券发放失败污染（rollback-only）导致整体回滚。三层问题逐一定位修复，最终实测消费 507 元自动升银卡、积分按 1.5 倍到账。这个故事体现了：日志追踪、时区意识、Spring 事务传播机制的理解。

### ★24. 系统有哪些不足？

**答**（如实）：
1. 微信支付为 Mock，未接真实商户；
2. 报表实时聚合，大数据量下性能受限（可演进数仓）；
3. 操作日志未覆盖所有新操作；
4. 4 类活动（新人/生日/沉睡/连续签到）触发逻辑已实现但未接自动定时入口；
5. 无监控告警体系；
6. DLQ 重放无分布式锁，多实例重复重放（幂等兜底不重复消费）。

### 25. 如果让你重构，会改什么？

**答**：1) 报表引入数仓/T+1 物化，减轻业务库压力；2) 统一操作审计 AOP；3) 活动触发全事件化；4) 引入 SkyWalkinig 链路追踪；5) 配置中心加密敏感项。

### 26. 为什么每服务独立数据库？

**答**：微服务的核心原则是数据私有。独立库强制服务通过接口交互而非直连表，降低耦合；独立账号最小权限；故障与升级隔离。例外是 report-service 的跨库只读账号（只读聚合场景，已说明取舍）。

### 27. 分布式事务怎么处理的？用了 Seata 吗？

**答**：没用 Seata（课程设计不引入重型框架）。按场景选择轻量方案：
- 「订单+事件」：本地 Outbox（同事务写事件表，异步投递）；
- 「钱包扣减+订单状态」：Saga 模式（oms_payment_saga 表记录步骤，失败补偿回冲）；
- 「营销发奖」：REQUIRES_NEW 独立事务隔离失败；
- 「退款冲正」：事件驱动 + 唯一索引幂等。
原则：能最终一致就不用强一致，资金操作必须有幂等与补偿。

### 28. 接口幂等是怎么实现的？

**答**：分层。写操作：唯一索引（uk_txn_biz 等）；事件消费：Inbox 表（与业务同事务）；高频接口：Redis setIfAbsent（如领券 800ms 锁）。测试验证：重复回调、重复投递、重复点击均不产生副作用。

### 29. 前后端如何联调的？金额怎么保证一致？

**答**：约定响应包装 {code,message,data,traceId}，code=0 成功；金额全链路整数分，前端仅做 fen2yuan 展示转换；所有金额由服务端试算接口（/api/order/quote）返回，前端不传金额。联调工具：19 个自动化测试脚本直接打网关断言。

### 30. 项目工作量与分工？

**答**（据实）：后端 9 服务 63 表 11 接口域、管理后台 28 页、小程序 26 页、测试脚本 36 个 246 断言、文档 20+ 篇。单人完成全部开发与测试，Git 提交记录可查（ea88296 起共 30+ 次功能提交）。
